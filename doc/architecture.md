# Gofi 目标架构

本文定义 Gofi 渐进式重构的边界和约束。目标是在保留现有可用功能的同时，让核心行为可测试、可替换、可维护，而不是一次性重写整个项目。

## 产品边界

Gofi 面向单机自托管场景，以本地文件系统为主要数据源，提供：

- 文件浏览、预览和下载。
- 登录后的上传与文件管理。
- 可配置的访客访问策略。
- 单二进制和容器化部署。
- 可选的本地文件索引与搜索。

当前阶段不以多节点存储、实时协作、桌面同步客户端或云盘协议兼容为目标。

## 架构原则

1. 先建立行为测试，再替换实现。
2. HTTP、业务用例和基础设施保持单向依赖。
3. 所有本地路径必须经过同一个安全路径解析入口。
4. 权限检查属于后端用例，前端路由保护只负责用户体验。
5. 文件写入优先使用临时文件、校验和原子替换。
6. 配置和数据库迁移在显式启动流程中完成，避免包初始化副作用。
7. 仅在存在真实替换需求或测试边界时引入接口。
8. API 错误具有稳定代码，同时使用正确的 HTTP 状态码。

## 后端边界

目标调用方向：

```text
HTTP transport
    -> application service
        -> storage / user / configuration ports
            -> local filesystem / SQLite adapters
```

M1 已建立以下渐进式结构。为控制一次性迁移风险，现有 Controller 和基础设施目录保留，新增边界按职责接入：

```text
gofi-backend/
  application/   认证、配置、文件和权限用例
  controller/    Gin 输入输出适配
  repository/    SQLite 数据访问适配
  storage/       本地文件系统安全边界
  middleware/    认证、安全、Trace 和请求治理
  db/            显式数据库打开、迁移和关闭
```

M2/M3 在相同边界中增加：

- `ResumableUploadService`：磁盘会话、分片校验、完成合并、取消和过期清理。
- `IndexService`：从本地存储生成可重建索引，文件变更后按路径前缀增量替换。
- `ShareService`：创建、解析、列出和撤销范围受限的分享令牌。
- `FileIndexRepository`、`ShareRepository`：只负责 SQLite 持久化，不读取用户文件。

### HTTP 层

- 解析和校验输入。
- 从请求上下文读取身份信息。
- 调用单个应用用例。
- 将领域结果或错误转换为 HTTP 响应。
- 不直接操作文件系统或数据库。

### 应用层

应用层使用明确的用例命名，例如：

- `BrowseDirectory`
- `GetFile`
- `DownloadFile`
- `UploadFile`
- `DeleteEntry`
- `ChangePassword`
- `UpdateGuestPolicy`

应用层负责权限、冲突策略和事务边界，不依赖 Gin 类型。

### 本地存储层

本地存储适配器统一负责：

- 将逻辑路径解析到存储根目录。
- 拒绝路径穿越、前缀碰撞和不允许的符号链接。
- 读取目录和文件元数据。
- 原子写入、移动、复制和删除。
- 统一文件系统错误。

业务代码不得自行使用 `filepath.Join(storageRoot, userInput)`。

### 上传层

普通上传已经通过临时文件和原子替换统一最终写入策略。旧分片上传实现无法安全恢复，已从 M1 移除；M2 重新实现时必须使用强类型会话并定义：

- 会话所有者。
- 目标逻辑路径。
- 文件大小、分片大小和分片数量。
- 内容哈希。
- 创建与过期时间。
- 已接收分片集合。
- 完成、取消和清理状态。

内存实现可以保留用于开发，但必须并发安全；正式实现需要支持进程重启后的恢复。

## 前端边界

前端已经按产品能力组织，页面组件只组合相应 feature：

```text
gofi-frontend/src/
  app/
    App.tsx
    AppProviders.tsx
  features/
    auth/
    configuration/
    files/
    permissions/
    upload/
  shared/
    api/
```

### 状态原则

- 服务端数据由 SWR 管理。
- 临时交互状态保留在 feature 内。
- Token 和用户会话由统一 Auth 边界管理。
- Toast 由调用方根据语义触发，底层 HTTP 客户端不重复展示。
- API 错误必须保留稳定错误码、HTTP 状态和可本地化消息键。

### 文件功能拆分

当前文件页面已拆出：

- `useDirectory`：目录查询与重新验证。
- `useAccessCapabilities`：访客和登录用户能力矩阵。
- `useUploadTask`：上传阶段、覆盖确认和结果状态。
- 页面组件：路径导航、过滤、呈现与操作入口。

后续新增文件操作继续放入对应 feature，不把业务请求重新集中到页面组件或通用 HTTP 客户端。

## API 契约

当前 API 为兼容既有前端保留统一响应包裹。失败响应使用真实 HTTP 状态码，并至少包含稳定数字码、消息和 Trace ID：

```json
{
  "success": false,
  "code": 404,
  "message": "资源不存在",
  "traceId": "request-trace-id"
}
```

成功响应当前为 `{"success":true,"code":200,"data":...,"traceId":"..."}`。任何后续契约变更都要先补测试，并在同一提交中更新前端调用方。

## 数据与迁移

- SQLite 在应用启动流程中显式打开并执行可重复 schema 同步，包初始化不创建文件或修改数据。
- `schema_migration` 记录当前 schema 版本；高于程序支持版本的数据库会拒绝启动。
- 密码散列升级采用登录时迁移或一次性迁移策略，不能让现有用户静默失效。
- 配置读取顺序和默认值必须文档化。
- 存储目录中的用户文件永远不参与应用迁移或自动删除。

## 测试边界

最低测试组合：

- 路径解析器表驱动测试。
- 本地存储临时目录集成测试。
- 认证与权限矩阵 HTTP 测试。
- 上传、Range 下载和错误契约测试。
- 前端路径、API 映射和关键交互测试。
- 构建后的静态资源和单二进制启动冒烟测试。

架构调整只有在相关测试先建立或同时建立时才算完成。
